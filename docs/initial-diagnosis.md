# 学习通助手 V0.1 安装与启动核查

核查对象：用户指定的 `chaoxing-app/release-final/ChaoxingHelper-V0.1-win64` 及对应 ZIP。另核对了相邻源码、Electron 运行时与构建器代码，并经用户授权与 DeepSeek 原开发会话直接核对。

## 结论

安装失败的直接原因已经复现：安装脚本使用纯 LF 换行，在本机 cmd.exe 下被错误解析。发布包还存在语言文件全部被过滤、日志路径不可写、安装说明与文件名不一致等缺陷。直接启动的原目录进程出现原生层崩溃；相同 EXE 的工作区副本在正常执行权限下可以正常显示界面。因此不能认定业务源码整体不可运行，也不能把语言文件缺失或杀毒误报当作已确认的闪退根因。

## 1. 安装脚本：确定的失败原因

- `install.cmd`：UTF-8，43 个 LF、0 个 CRLF；`uninstall.cmd`：34 个 LF、0 个 CRLF。脚本还指定了代码页 936，与 UTF-8 文本不一致。
- 在工作区制作保留原语法与编码的诊断副本，仅将安装目标指向工作区，并在创建快捷方式前停止。原换行版出现多条“不是内部或外部命令”，例如 `level`、`stalling` 被当作命令，退出码为 1。
- 仅改成 CRLF 后，同一复制阶段退出码变为 0。再统一成 UTF-8 + 65001 + CRLF，复制阶段也通过。
- 这一测试确认复制阶段的解析问题已解决；没有把它表述为完整安装、快捷方式或卸载验收通过。

修复：两个 CMD 统一为 CRLF，并统一字符编码与代码页。建议简化 PowerShell 多行续行。快捷方式创建、启动步骤应检查退出状态并保留错误输出，当前脚本直接隐藏错误、显示完成，不足以证明安装成功。

## 2. 语言文件：确定的打包缺陷，来源已验证

- 原始 `vendor/electron/dist/locales` 有 55 个 `.pak`。
- `release-build/win-unpacked/locales`、发布目录与 ZIP 均没有语言文件。
- DeepSeek 回溯最后打包命令使用了 `--config.electronLanguages="zh-CN,en-US"`。
- 我用本地已安装的 electron-builder 25.1.8 参数解析器与 builder-util 实测：该参数得到字符串 `zh-CN,en-US`，经 `asArray` 转换得到 `["zh-CN,en-US"]`，并不会拆成两种语言。
- 构建器 `ElectronFramework.js` 使用精确语言名匹配，对 55 个语言文件计算，保留结果为空。这解释了为何目录在 win-unpacked 阶段已经被清空。

修复：去掉此过滤参数，或在构建配置使用真正的数组，如 `"electronLanguages": ["zh-CN", "en-US"]`。若保留全部语言，构建后应断言有 55 个文件；若限定中英文，则应断言这两个目标文件存在。不能只断言 EXE/ASAR 存在。

缺语言的工作区副本仍能创建窗口，只是输出大量 `locale resources are not loaded` 警告，因此本缺陷不是已证实的单独闪退原因。

## 3. 启动失败：已经确认的范围与尚未确定的部分

- 从原始目录启动，退出码为 `0x80000003`（EXCEPTION_BREAKPOINT）。原包带有的 `debug.log` 只有两条 `crashpad_client_win.cc(868): not connected`。这类日志本身不能确定是哪一个底层初始化条件失败。
- 原始 vendor Electron 的最小探针在该环境中也出现相同退出码，未到 JavaScript 探针的首条日志。
- 复制到 Codex 工作区并正常权限运行后，窗口标题为“超星慕课 — 学习通助手”。经桌面观察，控制面板、就绪日志及学习通公开首页均已加载。没有依赖永久关闭 sandbox。
- 原 EXE 和工作区副本的 SHA-256 完全一致，说明这一差异不能用 EXE 字节损坏解释。
- 原目录与副本目录的 ACL 确有差异；运行目录、执行令牌/进程约束是下一步重点。但本轮没有确认具体是哪条 ACL 或哪项原生初始化条件造成崩溃，不能把推断写成定论。
- 受限执行环境下补齐语言文件仍然崩溃；因此测试环境本身会影响结果，单次闪退不能作为修复失败的充分证据。

DeepSeek 明确回复：此前的 Electron 验证没有成功到达 `whenReady`，此前成功的是资源结构检查与打包产物检查，而非完整安装启动验收。它还回溯到构建时的符号链接、图标资源和 NSIS 编译错误；这些历史错误不等于当前 ZIP 安装失败的直接原因。

## 4. 日志失效及交付不一致

- `main.js` 把 `BOOT_LOG` 设置为 `path.join(__dirname, 'boot-error.log')`。打进 `app.asar` 后，此路径位于归档内部，无法正常追加文件；捕获分支又静默吞掉错误。这解释了为什么没有可用的应用启动日志。
- 修复：使用 `app.getPath('userData')` 或独立可写日志目录，并在写日志失败时至少输出 stderr；捕获启动异常后应明确展示失败。
- README 要求双击“一键安装.cmd”与“卸载.cmd”，实际交付名是 `install.cmd` 与 `uninstall.cmd`；说明中的快捷方式名称也与脚本生成名不同。
- 发布包混入了开发阶段的 `debug.log`，不能把该日志的旧内容当成本次运行证据。

## 建议的最小修复与验收

1. 修正两份 CMD 换行和编码、构建语言过滤、启动日志路径及 README。
2. 重新打包后先检查所需语言文件与 ASAR 内容，再解压到普通用户目录，保留系统安全设置。
3. 先直接启动 EXE，确认窗口内容、公开首页、日志和正常退出；然后独立验收安装复制、快捷方式、再次启动与卸载。
4. 若仅特定原目录仍崩溃，对照目录 ACL 与实际运行令牌，采集原生崩溃转储定位具体失败点。不要用永久禁用 sandbox 或关闭防护作为修复。

本轮没有修改原项目源码、重打包、正式安装或卸载；只操作诊断副本，并已关闭测试应用。没有登录账户、播放课程或操作测验。界面启动通过不代表业务功能已通过验收。
